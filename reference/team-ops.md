# 阶段 4–5：组队、任务板与协作机制（DHS 0.2.2）

## 工具速查

| 工具 | 用途 | 要点 |
|---|---|---|
| `subagent` | 创建成员 | 参数 `description`、`prompt`、`name`（小写字母/数字/连字符，≤32 字符，`lead` 保留给根）、`cwd`；执行类成员加 `provider` + `model` + `reasoning_effort: "high"`（SKILL.md 上下文纪律 8）。立即返回名字；成员不共享你的对话，prompt 必须自包含。能同时做的几个成员在同一次回复里一起创建。 |
| `list_subagent_models` | 查可用的 provider、model 和思考档位 | 开工时查一次，结果写进 STATE.md「概况」。 |
| `subagent_fork` | 创建继承你当前对话的成员 | 只在成员确实需要你的上下文时用；更贵。 |
| `send_message` | 给任意成员发消息 | 参数 `agent`（名字，以 `list_agents` 显示为准）、`message`。空闲成员收到消息会开始新一轮。 |
| `wait_agent` | 等下一条消息/完成通知 | `timeout_ms` 10000–3600000。不要轮询。 |
| `list_agents` | 看整棵成员树 | `inactive` 只表示当前没在跑，不表示完成或失败。 |
| `interrupt_agent` | 让成员停下 | 只有祖先能中断。之后可以用 `send_message` 继续。 |
| `team_task_create` | 建任务 | `subject`、`description`、`blocked_by`（任务 id 列表）、`write_scopes`（路径前缀）。 |
| `team_task_list` / `team_task_get` | 看任务 | 有 `ready`、`owner`、`revision`、写入范围冲突警告。 |
| `team_task_update` | 改任务 | 必须带最新 `expected_revision`。action：`claim` `release` `edit` `set_dependencies` `complete` `reopen` `reassign`（仅 Lead，`owner` 填成员名） `delete`。 |

团队工具只在根会话打开"启用智能体团队协作"（模型名菜单里的开关）后才出现。工具缺失时见 SKILL.md 阶段 0 的降级方案。

## 按缺口招人

先看全貌缺什么能力，再从下表挑。没有对应缺口的角色不要招；串行的活你自己做，不拆给人接力（SKILL.md 铁律 7）。成员数受 `.team/guard.json` 的预算约束（SKILL.md「派几个人」），超出会弹窗请用户批准。

| 角色合同 | 招它的信号 | 读写 |
|---|---|---|
| `roles/scout.md` 勘察员 | 已有代码库要摸底；需要查资料、竞品、文档 | 只读 |
| `roles/critic.md` 方案评审 | 中/大项目方案拍板前：一个人从产品、工程、界面、反方四个角度挑刺 | 只读，写一份评审 |
| `roles/product.md` / `roles/architect.md` | 只在方案评审员发现某一面问题特别大、需要深挖时再单独派 | 只读 |
| `roles/designer.md` 设计师 | 有界面要新做或改；新功能要放进现有界面 | 写 `PRODUCT.md`、`DESIGN.md`、界面代码 |
| `roles/builder.md` 实现者 | 有代码要写。按模块/写入范围可招 1–3 个 | 写自己任务的写入范围 |
| `roles/writer.md` 写手 | 小说、剧本、文案等要读者买账的正文。相邻章节一次只派一个 | 写自己任务的章节 |
| `roles/reviewer.md` 评审员 | 任何写代码的项目都要有（可以由一个成员兼顾全部评审） | 只读，出评审报告 |
| `roles/qa.md` 测试验收 | 有可运行的产物需要实跑验证 | 写测试和 `.team/qa/` 证据 |
| `roles/docs.md` 文档 | 用户可见功能多、文档多，或里程碑收尾 | 写文档 |
| `roles/compliance.md` 合规评审 | 受监管行业（医疗、金融、政务、教育）、有国产化/信创要求、处理个人敏感信息 | 只读，写合规矩阵 |

编制见 SKILL.md「派几个人」。有界面的中/大项目在定方向时加设计师，定完就退场。测试验收、文档成员只在大项目的里程碑关卡需要时才派；平时由实现者在任务里补测试和文档。

## 命名

成员名用角色加范围：`scout`、`critic`、`designer`、`builder-api`、`builder-web`、`reviewer`、`qa`、`docs`。界面靠开头的角色词显示"实现（builder-api）"这样的大白话，所以角色词必须放在最前面。调用 `subagent` 时一定要传 `name`：不传 DHS 会自动起名 `agent-1`，界面就认不出这是谁（11-17 实测）。

## 任务板规则

- 一个任务 = 一个可以独立验收的结果，最好一个成员 40 步以内能做完。太大就拆。
- 任务标题写大白话（"做记账页"，不写"实现 LedgerView 组件"）：它会原样显示在流水线上。
- 描述按 `templates/task-card.md` 写，必须有：目标、验收标准（可检查）、要更新的文档、写入范围、完成后交给谁。复杂或高风险任务（状态流转、计费、并发、对外接口、迁移、复杂界面）另外给 1–3 把方法钥匙（来自 `plain-to-meta` 分册），写清在本任务里具体要求什么。
- `blocked_by` 只写真依赖。设计方向定了才能做界面；接口定了前后端才能并行。
- **写入范围互不重叠才能并行。** 两个任务都要改同一个文件（路由表、公共类型、样式变量），把那部分拆成一个先做的小任务，其余任务依赖它。
- 评审也建成任务，依赖对应的实现任务，这样任务板能看出质量关卡走到哪了。首件先评（第一章、第一个界面）不走这条依赖：lead 直接 send_message 请评审看，看完再继续。
- 任务完成后不要删除；要改范围就 `edit` 并在描述里写原因。
- 大项目只为当前里程碑建任务；任务主题加里程碑前缀（如 `[M2] 订单列表分页`），方便跨里程碑对账。

## 并行写代码：worktree 与合并

写入范围能做到完全不重叠时，成员可以在同一个工作目录里并行。做不到、或中/大项目有 2 个以上实现者同时写代码时，用 git worktree 隔离：

1. **开 worktree**（Lead 执行，每个实现者一个）：

   ```
   git worktree add ../<项目名>-wt-<成员名> -b team/<里程碑>-<成员名>
   ```

   放在项目目录**外面**的同级目录，避免被构建工具、测试和 skill 发现扫进去。
2. **派成员时**用 `subagent` 的 `cwd` 指向它的 worktree，brief 里写明："你的工作目录是 <worktree 路径>，只在这里改；`PROJECT.md`、`DESIGN.md` 等共享文档以主目录 <路径> 的为准，只读。"
3. **成员完成**：在自己的 worktree 里跑 `verify` 通过 → 提交到自己的分支（只提交，不合并、不推送）→ `send_message` 给 Lead，附分支名和 `verify` 输出。
4. **合并**（Lead 或指定的集成成员执行，评审通过后）：在主目录把分支合进来 → 跑 `verify` → 通过才算合并完成；冲突或失败就退回给原实现者，在它的 worktree 里解决。一次合并一个分支，合并完再合下一个。
5. **清理**：分支合并并验证后 `git worktree remove <路径>`，删分支前确认已合并。里程碑结束时 `git worktree list` 应该只剩主目录。
6. 共享文件（路由表、公共类型、样式变量、依赖清单）仍然只允许一个任务改；其他任务依赖它，等它合并后再基于最新主分支开 worktree。

worktree 的分支提交属于团队内部过程，不需要每次问用户；成员在 worktree 里的 commit 插件不弹窗；合并进主分支后的提交、以及任何 push，由插件弹窗请用户批准（或用户已做里程碑整批授权）。

## 成员轮换

成员是独立会话，上下文会越来越重，每一步越来越贵，质量也会下降。按 `templates/handoff.md` 的规则换人：

- 换人的信号：插件提醒过 120 步、里程碑结束、同一任务退回超过 2 次、回报质量明显下降。
- 相关的下一个任务、而成员的对话还不长（没收到过步数提醒）：继续交给它，比新人从头读便宜。
- 离开的成员先写交接单 `.team/handoff/<成员名>.md`；新成员的 brief 附上交接单路径。
- 旧成员写完交接单后不再给它派活，在 `STATE.md` 的团队表里标"已退场"。
- 评审员可以跨一个里程碑保留，保持评审标准一致；实现者默认每个里程碑换一批。

## 交接协议

成员和 Lead 之间的消息保持短而完整。格式固定（驾驶舱从会话记录里读它，画成任务节点上的"凭什么说做完了"）：第一行固定，之后每个标签单独一行、以全角冒号结尾，顺序不限，没有内容写"无"。

```
[任务 task-N] 完成 / 阻塞 / 需要决定
结果：一句大白话（不懂技术的人能看懂）
交付：文件或目录路径，多个用"；"隔开（应在任务的写入范围内）
检查：命令 → 结果，多条用"；"隔开（例如 `pwsh -File verify.ps1` → exit 0，27/27 通过）
偏离：会影响用户的取舍，一句话、60 字以内、不写文件名和代码："遇到 X，选了 Y"；纯技术细节写进报告文件；没有就只写"无"
文档：更新了哪些文档（或"无行为变化，不需要"）
未验证：没跑、跑不了的检查和原因
遗留：没做的、发现的风险
```

- `检查` 只写真跑过的；`未验证` 不能省（没有就写"无"），这样节点上能分清"有证据"和"没证据"。
- 插件在发的那一刻检查 `偏离` 行：带文件名、路径、命令、代码引号或超过 80 字，消息被退回，改好再发（11-18 大项目实测成员不照手册写，只能当场拦）。
- `偏离` 会显示在流水线的"团队替你定的事"里给用户看：只写会影响用户的取舍（数据怎么存、某个情况怎么处理、砍掉了什么），不写纯技术细节。Lead 把影响大的抄进 STATE.md，需要用户拍板的变成 waiting。

- 成员完成任务：先 `team_task_update complete`，再 `send_message` 给 Lead（和合同里写的下一个接手人）。用 worktree 的成员附上分支名。
- Lead 每处理完一次交接，更新 `.team/STATE.md`（进行中的任务、下一步）。
- Lead 退回：`team_task_update reopen`，再 `send_message` 写清具体问题和期望的证据。
- 解除阻塞：Lead 发消息通知被阻塞任务的负责人可以开始了。

## 等待用户拍板时

- 节点①②③等用户回答期间，只能派**不依赖这个决定**的活（例如勘察、只读调研）。依赖方案或设计方向的任务，等用户拍板后再派，否则用户选了别的就白做了。
- 一个问题里打包多个小默认值（"以下 6 点都按推荐"）可以，但每个默认值都要在问题里列出来，用户能单独改其中一条。

## 控制篇幅和成本

实测（2026-11）：一个单页"习惯打卡"小工具派了 7 个成员、15 个任务，读取量约 1.6 亿；最贵的两个成员各自在 20 万以上的上下文里走了 160–180 步。按本手册重跑（11-17）：同类命令行工具约 650 万，三模块的共享购物清单约 3620 万，其中三分之二花在 Lead 自己身上（Lead 走到 108 步、上下文 25 万）。所以：

- 11-19 拆了时间账：模型时间九成在生成输出，其中七到八成是思考；上下文长短不影响生成速度（约 195 字/秒）；工具时间六成是 Lead 在 `wait_agent` 等成员；小、中项目同一时刻基本只有一个人在干活。所以提速靠三件事：能并行的同时派、执行类成员降一档思考、过程文档只写机器要的。少读上下文主要省 token。
- 先只为并行和独立评审派人（SKILL.md「派几个人」），再管住每个成员的步数和上下文（SKILL.md「上下文纪律」）。
- Lead 自己也是成员：一个里程碑做完、或收到 120 步提醒时，按 `reference/resume.md` §4 换新会话接着做，别让一段对话涨到几十万。
- 评审、勘察报告结论先行，一行一条，一般不超过 100 行；证据给路径和关键输出，不整段粘贴。勘察结论写进 `.team/map.md`，后来的成员读这份地图，不再各自摸代码库。
- `DESIGN.md`、`PROJECT.md` 写规则和决定，不写推导过程；写法按 `reference/docs-and-retro.md` §4（给机器读）。
- 流水线底部的"用量"会列出负责人和每个成员各用了多少。交付报告里写上总量和最多的那一个，复盘时看要不要缩小编制。

## 卡住时

- 成员 2 次以上用同样方法失败：让它停下，写下已经试过什么，换人或换方法。
- 评审来回超过 3 轮：Lead 介入，判断是标准不清还是方案有问题；方案有问题就回到阶段 2。
- 发现方案层面的问题（比如原定的库做不到）：不要让成员自己改方向。Lead 评估影响，必要时按铁律 2 问用户。
