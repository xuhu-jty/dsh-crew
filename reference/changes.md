# 需求变更与想法管理

用户的想法会很多，需求会临时变。这是正常的，不是干扰：好的团队不是拒绝变更，而是让每次变更**看得见代价、由用户决定、不打乱正在进行的工作**。

## 1. 任何时候用户提出新想法或改需求

Lead 先接住，不要立刻改任务，也不要立刻说"这超出范围了"。按顺序做：

1. **记下来**：写进 `PROJECT.md` 的"变更与想法"表，编号 `CR-N`，原话照录。
2. **评估影响**（能查的自己查，必要时派架构评审或合规评审看一眼，要快，几分钟级）：
   - 改的是什么：新增功能 / 改已有行为 / 改方向。
   - 影响哪些已完成或进行中的东西：模块、接口、数据结构、已验收的里程碑、文档。
   - 代价：大概多少任务（S/M/L）、要返工什么、会推迟哪个里程碑。
   - 风险：合规、数据迁移、安全、和已定决定冲突的地方。
   - 有没有更小的做法能满足同样的目的。
3. **给用户选**（按铁律 2，附推荐）：
   - **A 现在做**：插进当前里程碑。说清楚会推迟什么。
   - **B 下个里程碑做**：当前里程碑不受影响。
   - **C 放进想法池**：先不排期，以后每个里程碑验收时回顾一次。
   - **D 不做**：说明原因（和目的冲突、代价远大于价值、合规不允许）。
4. **用户选定后**：更新 `PROJECT.md`（范围、里程碑、仍有效的决定）、`STATE.md`、任务板。改动已在进行的任务时，先 `send_message` 通知负责的成员再 `edit` 任务。
5. **改到了需求的五节**（目的 / 用户与场景 / 成功标准 / 范围 / 假设）：界面会马上显示"需求改过，等你重新确认"。告诉用户这五节具体改了哪几句，用户明确说确认后再运行 `doc-check.mjs --confirm`。用户还没确认时，按改之前已确认的需求继续做，不按新写的需求开工。勾选做到的成功标准不算改，不用确认。

## 2. 保护正在进行的里程碑

- 默认推荐 B 或 C：当前里程碑已经在做，频繁插入会让什么都做不完。只有满足下面任一条才推荐 A：不做的话当前里程碑的成果会作废；是 bug 或合规问题；用户明确说很急。
- 改方向（不是加功能）的变更：停下来，当作重新走一次节点②，和用户确认新方向后，评估已完成工作哪些还能用。
- 同一个里程碑内连续插入超过 3 个变更：提醒用户一次，问是否要重新划分里程碑。
- 改了已经做完的前面部分（改前几章、改一个被后面调用的接口、改一条被后面引用的设定），后面已经做完的东西不会自己跟着变。改之前列一张"改了哪些事实"的单子（谁见过谁、谁在哪、多少人、谁知道什么、哪个东西已经用掉），改完逐条在后面的章节或代码里搜一遍，对不上的列进同一个里程碑一起修；评审说"后面没动、不受影响"要拿搜索结果作证据。11-21 小说项目 M9 把岳飞提前到第 9–10 章当面受密旨回相州募兵，第 21、23、25、26 章仍写成皇帝托人"在相州军中寻一个姓岳的"、岳飞带十一骑初次来投，评审第二遍却写"ch12–31 未动、与密旨呼应"。
- 质量线或对标提高了：先按新线把已经做完的部分体检一遍（逐章、逐个界面打分，列出最弱的几处），从用户最先接触的地方往后修到过线，再继续做新的。新东西是叠在旧东西上的：地基不过线，后面做得再好也白做（11-21 小说项目写到第 30 章才把线提到"对标 10 分、12 分过线"，先停下体检前 30 章，再写第 31 章）。

## 3. 用户的想法可能有局限，团队要说实话

用户是拍板的人，但团队的责任是把看到的问题说出来：

- 想法和已确认的目的、合规要求、已定架构冲突时，直说冲突在哪、后果是什么，给出替代做法。不顺着说好。
- 想法背后可能有更好的手段时，复述用户真正想达到的目的，给出 1–2 个更好的做法供选。
- 说完一次，用户仍然坚持，就按用户的决定做，并在"仍有效的决定"里写下这条决定和它的风险。不反复争论。

## 4. 想法池回顾

每个里程碑验收（节点④）时，把想法池过一遍：哪些现在值得排进下个里程碑、哪些可以删掉。给用户一张短表，用户勾选。
