# 阶段 2：全景、方案与三视角评审

## 1. 摊全貌（写进 PROJECT.md 的"全景"）

一个整体缺了下面任何一块就不成立。逐项写，不适用的写"不适用"和原因：

- **用户流程**：从第一次打开到达成目的的完整路径，包括回访、出错后怎么恢复。
- **模块**：系统由哪几部分组成，各自负责什么，怎么互相调用。
- **数据**：从哪来、存哪、怎么变、到哪去；谁能读写；要不要迁移旧数据。
- **状态**：每个界面/接口的加载、空、错误、无权限、部分成功状态。
- **接口与集成**：必须接上的现有系统、第三方服务、它们挂了怎么办。
- **运行**：怎么本地跑、怎么部署、配置和密钥放哪、日志和监控、备份与回滚。
- **验证**：现在靠什么证明它是对的（测试、类型检查、实跑脚本），这次要补什么。

已有代码库还要写：**哪些现有行为必须保持不变**，以及怎么一步步迁过去而不停摆（先加新路径、再切流量、最后删旧代码）。

## 2. 出方案（2–3 套，真正不同）

```
方案 A：<名字>（最小可行）
  概要：1–2 句
  工作量：S / M / L / XL
  风险：低 / 中 / 高
  优点：2–3 条
  缺点：2–3 条
  复用：用到哪些现有代码、库、平台能力
方案 B：<名字>（理想架构）
方案 C：<名字>（另辟蹊径，可选：换个角度看问题，或者借别的行业的做法）
推荐：X —— 一句理由，对上用户确认的目的
```

规则：

- 至少两套；每套都要能独立成立，不是同一方案的大小号。
- 借别的行业的方法时，说清它改变了方案的哪一步，并把改变直接做进方案里。只换说法不算。方法可以从 `plain-to-meta` 的分册里挑（装了时）（软件架构看 05，数据与决策看 04，界面看 01/07，汇报看 03）；分册没有的领域，用它的"奠基人溯源法"找具名方法，不生造行话。阶段 1 的 `.team/request-upgrade.md` 里已经挑出的钥匙，在方案里要看得到落点。
- 每个关键技术选择先查"运行时/框架有没有内置的、现有依赖能不能做"，再考虑新写或加依赖。

### 创新放在哪一层

创新要放在能带来价值、又不增加不可控风险的那一层：

- **基础设施保持稳妥**：受监管或关键业务系统（医疗、金融、政务、生产控制等）的底层（数据库、中间件、协议、加密、部署架构）用成熟、经过验证、能通过测评认证的方案。新奇的底层技术在这里是风险，不是创新。非关键系统也默认如此，只有确有理由时才花"创新额度"。
- **创新放在三处**：
  1. **工作流程**：用户完成一件事的步骤能不能更少、更顺，能不能少录一次、少跳一个系统、少等一次。
  2. **使用体验**：用户第一眼看到什么、出错时怎么恢复、高频操作是不是一步到位、信息是不是在需要时自动出现。
  3. **交付方式**：怎么拆分、排序、取证、上线，让项目更早产生真实价值、更早暴露风险。
- **每套方案至少写一条工作流程或体验上的创新**，并写清可衡量的好处（例如"开一张检验单从 7 次点击降到 3 次""结果回来自动出现在下次接诊的首屏"）。说不出可衡量好处的，不算创新。
- 产品评审检查这一条；设计方向（节点③）必须把这些流程创新画出来，不能只换视觉风格。

## 3. 三视角评审（并行、只读）

给三个评审员同样的材料（`PROJECT.md` + 方案），各自按合同出意见。每个视角都必须**专门找能推翻方案的证据**，而不是顺着说好。

- **产品视角**（`roles/product.md`）：
  - 这是不是在解决对的问题？是不是在解决一个替代品（proxy）问题？
  - 10 倍好、只多花 2 倍力气的版本长什么样？有哪些 30 分钟就能做、用户会觉得"他们想到了"的细节？
  - 反过来想：什么会让这个项目失败？
  - 做减法：哪些东西不做反而更好？
- **工程视角**（`roles/architect.md`）：
  - 每个子问题现有代码里有没有现成的？能不能复用现有流程的输出，而不是平行再造一套？
  - 实现目标的最少改动是什么？方案涉及 8 个以上文件或新增 2 个以上服务/类时，当作危险信号，看能不能少一些部件。
  - 架构、数据流、失败模式（每个外部调用失败时会怎样）、并发、性能、安全。
  - 测试计划：哪些逻辑必须有测试（分支、解析、金额、安全、数据写入、修 bug）。
  - 能不能逆转：用开关、灰度、先加后删，把犯错的代价降低。
- **设计视角**（`roles/designer.md`，有界面时）：
  - 信息架构：用户第一眼、第二眼、第三眼看到什么？
  - 新功能放在现有界面的哪里，为什么放那里，会不会挤占或打乱已有功能？
  - 空、错、加载状态；长文本、零结果、网络中断、新手与老手。

### 反方检验（推荐方案定下之后、问用户之前）

派一个**没参与推导**的评审员（全新上下文，只给它 `PROJECT.md` 和方案），任务只有一个：假设推荐方案是错的，找出最可能推翻它的证据、反例和边界情况，并推演它对其他模块、用户习惯、系统复杂度和长期维护成本的二阶影响。你自己审自己的方案效果很弱，所以这一步必须交给别人。它找到推翻性证据就回到第 2 节；找到的是风险就写进方案。小项目（轻量通道）跳过。

## 4. 拆里程碑

- **每个里程碑是一个能演示的完整切片**：用户能在里面走通一条真实流程（从界面到数据），而不是"后端全写完""所有页面画完"。横着切（按技术层）会让问题到最后才暴露，竖着切（按用户流程）每个里程碑都能验证方向。
- 顺序：里程碑 0 地基（中/大项目）→ 风险最高、最能验证方案的那条流程 → 主流程其余部分 → 次要流程 → 打磨与收尾。先做风险最高的，方案有问题能尽早发现。
- 每个里程碑写清：目标（一句话）、演示什么（用户会看到/操作什么）、验收标准（可检查）、涉及的模块、依赖哪个里程碑。
- 大小：一个里程碑一般 3–10 个任务。超过就拆。
- 只把里程碑 0 和 1 写细，后面的只写一句目标。每完成一个，根据学到的东西再细化下一个。
- **排序时先找三类"必须靠前"的事**，它们放晚了代价最大：
  1. **建设前置条件**（受监管项目）：法规要求在建设或设计之前就成立的事，例如安全等级定级与备案、密码应用方案评估、产品是否属于需要注册/许可的类别。单独设一个**里程碑 M-1：合规前置门**，不写代码，产出这些事项的结论或已提交的申请；不通过，M0 不开工。
  2. **横切架构约束**：一旦晚了就要改遍全系统的东西，例如加密/国密、审计留痕、签名、多租户/数据隔离、编码标准与字典模型。放进 M0 冻结，后面的里程碑只做落地。
  3. **决定项目能不能成立的外部事实**：例如旧系统数据能否导出、外部接口规范和测试环境能否拿到。在 M0 期间做小样本取证（抽几条真实样本试一下），拿不到就当场和用户重新定义项目，不要等到后面的里程碑才发现。
- **外部依赖单独排"并行跑道"**（编号 P1、P2…，不占里程碑号）：采购、证书、外部接口申请、硬件、第三方联调这类"等别人"的事，从 M0 起就启动，每条写清负责人（通常是用户方）、预计周期、它会卡住哪个里程碑。里程碑只在依赖到位时才开工对应部分，没到位就用可切换的替身。
- **不可逆的真实数据动作要等依赖就绪**：会产生真实且不能撤回的数据的动作（真实用户/患者数据入库、具有法律效力的签名、归档封存、对外正式提交），在它依赖的正式组件（证书、签名服务、正式接口）就绪前必须关掉或只用测试数据，不要用替身产生真实记录。

## 5. 汇总给用户（节点②）

- 方案对比表 + 你的推荐 + 里程碑划分（每个一行：目标 · 演示什么）。
- 三个视角里**会改变推荐**的意见（不要全贴，挑最重要的 3–5 条），以及你怎么处理。
- 扩大范围的建议（10 倍版本、好细节）一条条列出，每条让用户选：加入本次 / 记到以后 / 不做。用户没选的不准偷偷加进来。
- 用户拍板后，写入 `PROJECT.md` 的"方案""里程碑"和"仍有效的决定"，同步状态卡，"不做"清单也写上，并更新 `.team/STATE.md`。团队不再主动反复争论已定的范围；用户之后提出的新想法和改动，按 `reference/changes.md` 的变更流程处理。
