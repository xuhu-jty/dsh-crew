# 里程碑 0：地基

中/大项目必做，小项目挑适用的做。地基是后面每个里程碑的前提：没有一条命令的验证，就没法判断"做完了"；没有锁住现有行为，就没法安全地改老代码；没有先定接口，并行开发就会对不上。

里程碑 0 也要有演示：给用户看 `verify` 跑通、特征测试覆盖了哪些行为、接口文档、怎么在本地跑起来。

## 0. 受监管项目：先过 M-1 合规前置门

法规要求"在建设之前就成立"的事（定级备案、密码应用方案评估、产品类别/许可等），在 M0 之前单独做一个 M-1：由合规评审列出清单和原文依据，用户方去办或提交申请，团队准备方案材料。M-1 的验收是"每项都有结论或已受理的申请凭证"。M-1 没过，M0 不开工；只有个别项周期很长时，经用户同意可以让 M0 中不受它影响的部分先开工，并写进决策记录。

## 1. 一条命令验证（verify）

- 在项目里放一个 `verify` 入口（`npm run verify`、`make verify`、`scripts/verify.ps1` 等，跟项目现有习惯走），依次跑：安装依赖、构建、类型检查、lint、测试。任何一步失败就整体失败。
- 在干净环境跑一次（新 clone 或新 worktree），确认能跑通，把命令和输出存 `.team/foundation/verify.txt`。
- 之后所有任务关卡、合并、里程碑关卡都以 `verify` 通过为前提。新增的检查加进 `verify`，不要散落在各成员的习惯里。
- 已有项目的测试本来就是红的：先记录"基线失败清单"，`verify` 只要求不新增失败；修基线另开任务，由用户决定要不要修。

## 2. 已有代码库：先锁住现有行为

改老代码之前，先让测试能告诉你"有没有改坏"：

1. **大仓库分片勘察**：按模块（或目录）派多个勘察员并行，每个只读自己那一片，产出该模块的地图；最后由一个勘察员（或 Lead）汇总模块间的调用关系。不要让一个勘察员读全库。
2. **特征测试**：对这次要改动的模块，在动手前写测试把**当前的**输入输出固定下来（哪怕当前行为看起来不对，也先如实记录，并在测试里标注"现状如此，待定"）。只给要改的部分写，不追求全库覆盖。
3. **逐步替换**：要换掉旧实现时，先加新路径（新函数/新接口/开关），让新旧并存；切流量；确认无误后再删旧代码。每一步都能单独回退。结构调整和行为变化不放在同一个任务里。
4. **必须保持不变的行为**写进 `PROJECT.md` 全景，每个相关任务卡引用它。

## 3. 接口先行

多个成员要并行开发互相调用的部分时：

- 先由架构评审（或 Lead）写下接口：API 路径和请求/响应、数据结构、事件、组件 props、错误码。放 `docs/` 或 `PROJECT.md` 附录。
- 能写契约测试的写契约测试（调用方和实现方都要通过），加进 `verify`。
- 接口改动必须先改文档、通知所有相关成员（`send_message`），再改代码。

## 4. 环境

- 本地运行：从零跑起来的步骤写进 README，并实际跑通一次。
- 测试数据：种子数据或夹具，能一条命令重置。夹具里的日期、时间从被测系统或固定时钟派生，不要硬编码"今天"。
- 外部服务（数据库、支付、短信、第三方 API）：本地用替身或对方的沙箱，写清楚怎么切换；真实凭据不进代码库，用 `.env`（不提交）+ `.env.example`（提交）。
- 需要用户提供的东西（账号、密钥、测试环境地址）一次性列清楚，按铁律 2 向用户要；没有时用替身推进，并在 `STATE.md` 记为阻塞项。

## 5. git 策略

- 主分支保持可用：只有通过 `verify` 和评审的改动才合并进去。
- 并行写代码的成员各用一个 worktree 和分支（做法见 `reference/team-ops.md`）。
- **提交授权**：第一次需要提交前，问用户一次："每个里程碑验收后由我提交一次，可以吗？"用户同意就写进 `STATE.md`，之后按此执行；不同意就只在交付时提醒用户自己提交。推送到远程、改历史、删分支始终单独问。
- 每个里程碑验收后一个提交（或一组提交），提交信息写里程碑名和主要变化。
