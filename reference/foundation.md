# 里程碑 0：地基

中/大项目必做；小项目（轻量通道）只做 §1 verify、§6 刹车与状态卡。地基是后面每个里程碑的前提：没有一条命令的验证，就没法判断"做完了"；没有锁住现有行为，就没法安全地改老代码；没有先定接口，并行开发就会对不上。

**地基也要演示**：verify 跑通、行走骨架能走一遍、特征测试覆盖了哪些行为、接口文档、怎么在本地跑起来。只有基础设施、没有一条能走通的业务流程的地基，不算完成。

## 0. 受监管项目：先过 M-1 合规前置门

法规要求"在建设之前就成立"的事（定级备案、密码应用方案评估、产品类别/许可等），在 M0 之前单独做一个 M-1：合规评审列出清单和原文依据，用户方去办或提交申请，团队准备材料。验收标准是"每项都有结论或已受理的申请凭证"。M-1 没过，M0 不开工；个别项周期很长时，经用户同意可以让 M0 中不受它影响的部分先开工，并记一条决定。

## 1. 一条命令验证（verify）

- 在项目里放一个 `verify` 入口（`npm run verify`、`make verify`、`verify.ps1` 等，跟项目习惯走），依次跑：安装依赖、构建、类型检查、lint、测试。任何一步失败就整体失败，退出码非 0。
- 在干净环境跑一次（新 clone 或新 worktree），确认能跑通。
- **verify 第一次真正跑通之后，再写进 `.team/guard.json`**（命令还不存在或跑不过时就写，收工前刹车会每轮把 agent 拉回来却无法通过）。刹车插件靠它判断"改了代码有没有跑验证"：

  ```json
  { "verify": "verify.ps1" }
  ```

  `verify` 的值是命令里能认出来的片段（插件按"命令里包含这段文字"识别）。
- 之后所有任务、合并、里程碑关卡都以 verify 通过为前提。新增的检查加进 verify，不要散落在各成员的习惯里。
- 已有项目的测试本来就是红的：先记录"基线失败清单"，verify 只要求不新增失败；修基线另开任务，由用户决定。

## 2. 行走骨架

地基阶段就打通**一条最薄的端到端流程**：从入口（界面或接口）到数据落地再返回，哪怕每一层都是最简实现或替身。例如医院系统：挂号 → 开一张处方 → 收费，用模拟医保和开发用签名桩。

为什么：后面每个里程碑都在这条骨架上加肉，问题在第一周暴露，而不是在第三个里程碑。基础设施（审计、签名、对接层）按骨架的需要做到"够用"，不先做完整。

## 3. 已有代码库：先锁住现有行为

1. **大仓库分片勘察**：按模块派多个勘察员并行，每个只读自己那一片；最后汇总模块间的调用关系。不要让一个勘察员读全库。
2. **特征测试**：对这次要改的模块，动手前写测试把**当前的**输入输出固定下来（哪怕当前行为看起来不对，也如实记录并标注"现状如此，待定"）。只给要改的部分写。
3. **逐步替换**：先加新路径让新旧并存，切流量，确认无误再删旧代码。每一步都能单独回退。结构调整和行为变化分开提交。
4. **必须保持不变的行为**写进 `PROJECT.md` 全景，相关任务卡引用它。

## 4. 接口先行

多个成员要并行开发互相调用的部分时：先写下接口（API、数据结构、事件、组件 props、错误码），放 `docs/` 或 `PROJECT.md`；能写契约测试的写契约测试并加进 verify；改接口必须先改文档、通知相关成员，再改代码。

## 5. 环境与 git

- **本地运行**：从零跑起来的步骤写进 README，并实际跑通一次。
- **测试数据**：种子数据或夹具，一条命令重置。日期、时间从被测系统或固定时钟派生，不要硬编码"今天"。
- **外部服务**：本地用替身或沙箱，写清怎么切换；真实凭据不进代码库（`.env` 不提交，`.env.example` 提交）。需要用户提供的账号、密钥、测试环境一次性列清楚；没有时用替身推进，在 STATE.md 记为阻塞。
- **git**：项目必须是 git 仓库（DHS 按 `.git` 认项目根，状态卡的自动注入也依赖它）。主分支只合并通过 verify 和评审的改动；并行写代码的成员各用一个 worktree（`reference/team-ops.md`）。
- **提交授权**（刹车插件执行）：
  - 默认：每次 `git commit` / `git push` 弹窗请用户批准；同一轮里重试同一个提交不重复弹窗。
  - 里程碑整批授权：用户验收里程碑后**本人**创建 `.team/commit-authorized`，这段时间提交不弹窗；下个里程碑开始时请用户删掉它。agent 不能创建或修改这个文件，伪造会被插件识别并删除。
  - 会话审批策略是"从不询问"时没法弹窗，提交会被直接拒绝：告诉用户切换到会询问的权限模式，或使用整批授权。
  - 推送到远程、改历史、删分支：始终单独问。

## 6. 刹车与状态卡

1. 确认 DHS 已装 `project-team-guard` 插件（安装见 skill 目录的 `README.md`）；没装就告诉用户后果（三个硬刹车退化成靠自觉），用户决定。
2. `.team/guard.json` 写好 verify 命令（§1）。
3. 按 `templates/state-card.md` 在项目根建状态卡 `AGENTS.local.md`，并把 `*.local.md` 加进 `.gitignore`。
4. 演示时让用户看到：改代码后不跑 verify 就收工会被拉回来；提交会弹窗。
