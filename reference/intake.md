# 阶段 1：读懂需求与追问

目标：开工前，你能用自己的话说清"这次为什么做、要做成什么样"，并得到用户确认。

## 0. 先升级用户的请求（用 plain-to-meta）

用户的原话往往是一个手段（"做个 X 系统"），不是目的。动手前先把它升级成专家级的任务描述，再拿去和用户确认。

- 全局装了 `plain-to-meta` skill（在 `~/.dsh/skills/plain-to-meta/`，和本 skill 同级）时，加载它，按它的四步引擎处理用户原话。注意：这里是**内部升级**，不是给用户改写提示词，所以不用它的"模式 B 编译器"格式，只取结果：
  1. **定向**：从表面动作还原终极目的；排查原话漏掉的前置环节（边界、状态、依赖、风险预案）；分清锁定和开放。
  2. **借力**：按痛点读它 `references/` 里**最相关的 1 个分册**，挑 1–3 把彼此正交的"方法钥匙"（具名方法，例如有限状态机、幂等与退避重试、绞杀者模式、渐进式披露、事前验尸）。每把钥匙写清：一句大白话解释 + **它改变方案的哪一步**。分册里没有的领域，用它的"奠基人溯源法"：痛点 → 所属严谨学科 → 经典教材或奠基人 → 具名定律。不许生造行话。
  3. **深挖**：列出要做实这件事需要的一手资料、可能推翻当前理解的反证、目前无法验证的地方。
- 没装 `plain-to-meta` 时，按上面三步手工做，并在 `STATE.md` 里记一句"未使用 plain-to-meta"。
- 产出写进 `.team/request-upgrade.md`，格式：

  ```
  用户原话：……
  升级后的目的：……
  补齐的前置环节：……
  方法钥匙：<钥匙名 (English)> —— 大白话解释 —— 改变方案的哪一步（1–3 条）
  要做实需要的一手资料 / 可能的反证 / 无法验证的地方：……
  ```

- 节点①确认时，把"升级后的目的 + 补齐的前置环节 + 方法钥匙"用几行给用户看（附大白话解释），让用户看得见请求是怎么被升级的，并能纠正。

## 1. 先读，再问

- **已有代码库**：派勘察员（`roles/scout.md`）出现状地图：技术栈、目录结构、入口、数据模型、现有界面和组件、测试和构建方式、现有文档、明显的问题。你读它的报告，不读整个仓库。
- **新项目**：读用户给的所有材料（文字、截图、链接、参考产品）。需要了解行业或竞品时，派勘察员查资料，要求它标明出处，二手说法和一手资料分开写。
- **改版/重构**：除了现状地图，还要找出"用户可能不满意的地方"作为你的猜测，带着猜测去问。重做的理由是不满意，不知道不满意什么，就只会把旧东西换个样子再做一遍。

## 2. 写出你的理解（交给用户确认）

```
目的：做完之后应该发生什么（不是"做一个 X"，而是"让谁能做成什么"）
用户与场景：谁、在什么情况下、多频繁地用
成功标准：怎样算成了（尽量可观察：能完成某流程、某指标、某人认可）
锁定的：用户明确要求 / 现有系统决定、必须照办的（技术栈、平台、品牌、接口）
开放的：团队可以选最好做法的地方
遗漏的前置工作：原话没提但缺了就做不成的（数据来源、账号权限、内容提供、迁移、部署环境、法律合规……）
我的假设：没问用户、先这样假定的事（用户可以纠正）
```

## 3. 追问的规则

- **事实和决定分开。** 能从代码、文档、网上查到的是事实，自己查。只问需要用户权衡的决定：取舍、优先级、品味、预算、时间、愿意放弃什么。
- **沿决策树一层一层问。** 每轮只问前提已经确定的 1–3 个问题；依赖本轮答案的问题下一轮再问。
- **每个问题都带推荐。** 格式：

  ```
  Q1 <决定是什么>：<一两句大白话说明两边的利弊>
  推荐：<选项> —— <一句理由>（回"是"即采纳）
  ```

- **用户的回答又带出关键新信息时，再问一轮**，直到你能复述清楚并得到确认。用户说"别问了直接做"时，最多再问 1 个最关键的，然后按你的推荐和假设推进，把假设写进 `PROJECT.md`。
- 用户的话里有含糊词（"高级""好用""快"），把它翻成能检查的标准，再请用户确认。例如"快"→"首屏 2 秒内可操作"。

## 4. 需求层面的挑战（问之前先在心里过一遍）

借鉴 YC office hours 的追问，按项目阶段挑着用，不要全问：

- **真实需求**：有什么证据说明真有人需要它？（行为，而不是"大家觉得有意思"）
- **现状**：用户现在怎么解决这个问题？土办法要花他们多少时间和钱？
- **具体到人**：最需要它的那个人是谁、他的一天哪里痛？
- **最窄切口**：最小的、别人这周就愿意用（或付钱）的版本是什么？
- **前提挑战**：这是对的问题吗？换个说法会不会简单得多？什么都不做会怎样？

内部工具、个人项目、纯工程任务只挑"现状"和"最窄切口"。

## 5. 产出

用户确认后：

- 写 `PROJECT.md` 的"目的""用户与场景""成功标准""范围（做 / 不做）""假设"部分（模板 `templates/PROJECT.md`）。
- 在决策记录里写下本轮用户拍板的每个决定和原因。
