# 阶段 1：读懂需求与追问

目标：开工前，你能用自己的话说清"这次为什么做、要做成什么样"，并得到用户确认。

## 0. 把需求升级（每个项目都做，小项目也做）

AI 默认会交出"这类东西的平均样子"。用户的原话往往是一个手段（"做个 X 系统"），不是目的；也可能把症状当成了原因。动手前先把原话**升级**，结果写进 `PROJECT.md` 的「升级」一节（模板见 `templates/PROJECT.md`），在节点①给用户看，用户能改。界面会把它显示在流水线的目标下面。

**第一步：读懂（必做）**

- **真正的目的**：做完之后应该发生什么？再问一次"然后呢"。用户说的东西是达到它的唯一办法吗？
- **锁定和开放**：哪些被情境锁定（现有技术栈、必须接上的系统、给谁用），照办；哪些只是用户顺手给的一种手段，是你发挥的空间。换手段会明显改变用户要付出的东西（钱、要学的、能不能接上现有系统）时，摆选项问，不悄悄换。
- **漏掉的前置**：原话没提、但缺了就做不成的（数据来源、账号权限、迁移、部署、合规）。
- **更值得解决的问题**：用户描述的是症状、原因在别处时，直接指出来，作为节点①的一个问题让用户选。

**第二步：往上推（必做，挑 1–3 个方向）**

装了 `amb` skill 时加载它，按它的思路来；没装就按下面四个方向。不必每个都推，挑能让这一次明显变好的：

- **速度**：同样的事更快交到用户手里（先交能用的一版，再迭代）。
- **高度**：从任务走到结果：用户要的照样交付，但它服务于更高的目标。
- **深度**：像这一行最顶尖的人那样做：他们会做、而用户没要求的是什么？用什么能证明结果是对的？
- **广度**：别的行当里谁天天在做这件事，借他们的方法（不是借口吻）。

挑的是推的方向，不是缩小范围：覆盖必须完整，重点处做到出色。

**第三步：借具名方法（中/大项目必做，小项目可选）**

装了 `plain-to-meta` skill 时加载它（内部升级，只取结果，不用它给用户改写提示词的格式）：按痛点读它 `references/` 里**最相关的 1 个分册**，挑 1–3 把彼此正交的"方法钥匙"（具名方法，例如有限状态机、幂等与退避重试、绞杀者模式、渐进式披露、事前验尸）。每把写清：一句大白话 + **它改变方案的哪一步**。只是换个说法、改变不了做法的不写。分册里没有的领域，用它的"奠基人溯源法"找具名定律，不生造行话。

**写进 `PROJECT.md`「升级」一节**（大白话，用户要能看懂）：

```
## 升级

从"<用户原话的要点>"到"<升级后要达成的结果>"。
- 方向：<高度 / 深度 / …>：<一句话说推到了哪>
- 方法：<钥匙名>：<改变了方案的哪一步>（中/大项目）
- 更值得解决的问题：<有就写，没有删掉这行>
```

第一行最重要：它会显示在流水线目标下面。小项目写第一行加一个方向就够。

节点①确认时，把这一节和"漏掉的前置"一起给用户看。用户不同意升级的方向，按用户的来，改掉这一节。

## 0.5 盲点扫描（用户不熟这个领域时）

用户第一次做这类东西（第一次做网页、第一次接支付、第一次碰医疗数据）时，他不知道该问什么、好的版本长什么样、坑在哪。先用大白话给他一页"你可能没想到的事"，再开始问：

- 这类东西通常要决定哪几件事（每件一句，说明为什么重要）；
- 最常见的 3 个坑；
- 好的版本和凑合的版本差在哪（尽量举用户见过的产品）。

这一页本身就是节点①的一部分，不单独停一次。用户熟悉这个领域时跳过。

## 1. 先读，再问

- **已有代码库**：小仓库你自己读（按目录和入口搜索，不整文件读）；大仓库才派勘察员（`roles/scout.md`）出现状地图，写进 `.team/map.md`，后来的成员都读它：技术栈、目录结构、入口、数据模型、现有界面和组件、测试和构建方式、现有文档、明显的问题。你读它的报告，不读整个仓库。
- **新项目**：读用户给的所有材料（文字、截图、链接、参考产品）。需要了解行业或竞品时，派勘察员查资料，要求它标明出处，二手说法和一手资料分开写。
- **改版/重构**：除了现状地图，还要找出"用户可能不满意的地方"作为你的猜测，带着猜测去问。重做的理由是不满意，不知道不满意什么，就只会把旧东西换个样子再做一遍。

## 2. 写出你的理解（交给用户确认）

```
目的：做完之后应该发生什么（不是"做一个 X"，而是"让谁能做成什么"）
用户与场景：谁、在什么情况下、多频繁地用
成功标准：怎样算成了（尽量可观察：能完成某流程、某指标、某人认可）
锁定的：用户明确要求 / 现有系统决定、必须照办的（技术栈、平台、品牌、接口）
开放的：团队可以选最好做法的地方
遗漏的前置工作：原话没提但缺了就做不成的（数据来源、账号权限、内容提供、迁移、部署环境、法律合规……）
我的假设：没问用户、先这样假定的事（用户可以纠正）
```

## 3. 追问的规则

- **事实和决定分开。** 能从代码、文档、网上查到的是事实，自己查。只问需要用户权衡的决定：取舍、优先级、品味、预算、时间、愿意放弃什么。
- **按影响排序，一层一层问。** 答案会改变架构或数据的先问，品味和细节后问。每轮只问前提已经确定的问题，依赖本轮答案的下一轮再问；拿不准时一次只问一题。
- **说不清的给样子看。** 用户对界面、风格、交互说不出要什么时，不追问形容词，做一页静态样稿（2–3 个方向、假数据）让他挑。用户能指出参考（某个产品、某段代码）时，读参考本身。
- **用大白话问。** 不用缩写和行话；非用不可的专业词，后面跟一句日常解释或比方。问的是用户的目的、取舍和底线，不是让用户替你做技术选型。
- **每个问题都带推荐。** 格式：

  ```
  Q1 <决定是什么>：<一两句大白话说明两边的利弊>
  推荐：<选项> —— <一句理由>（回"是"即采纳）
  ```

- **用户的回答又带出关键新信息时，再问一轮**，直到你能复述清楚并得到确认。用户说"别问了直接做"时，最多再问 1 个最关键的，然后按你的推荐和假设推进，把假设写进 `PROJECT.md`。
- 用户的话里有含糊词（"高级""好用""快"），把它翻成能检查的标准，再请用户确认。例如"快"→"首屏 2 秒内可操作"。

## 4. 需求层面的挑战（问之前先在心里过一遍）

借鉴 YC office hours 的追问，按项目阶段挑着用，不要全问：

- **真实需求**：有什么证据说明真有人需要它？（行为，而不是"大家觉得有意思"）
- **现状**：用户现在怎么解决这个问题？土办法要花他们多少时间和钱？
- **具体到人**：最需要它的那个人是谁、他的一天哪里痛？
- **最窄切口**：最小的、别人这周就愿意用（或付钱）的版本是什么？
- **前提挑战**：这是对的问题吗？换个说法会不会简单得多？什么都不做会怎样？

内部工具、个人项目、纯工程任务只挑"现状"和"最窄切口"。

## 5. 产出

用户确认后：

- 写 `PROJECT.md` 的"目的""用户与场景""成功标准""范围（做 / 不做）""假设"部分（模板 `templates/PROJECT.md`）。
- 在"仍有效的决定"里写下本轮用户拍板的每个决定和原因；同时建状态卡 `AGENTS.local.md`（`templates/state-card.md`）。
- 把写好的这五节给用户过目（用户在流水线标签页也能看到）。用户在对话里明确说确认后，运行 `node <skill 目录>/scripts/doc-check.mjs --confirm <项目路径>`，它把这五节的指纹记进 STATE.md 文件头的 `confirmed`。用户没明确说确认，不许运行；不许手写这一行。
