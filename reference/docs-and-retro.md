# 文档原则与复盘沉淀

项目越大，旧文档越会变成噪音：后来的人（包括换了会话的你）会照着过期内容干活。所以文档只描述**现在**，历史压成一句话，过程文件用完就清。复盘也一样：不只记"发生了什么"，而是把反复出现的问题变成下次会自动生效的东西。

## 1. 文档分四类，处理方式不同

| 类 | 例子 | 规则 |
|---|---|---|
| **活文档** | `AGENTS.local.md`（状态卡）、`.team/STATE.md`、`PROJECT.md`、`DESIGN.md`、`README.md`、`docs/` 接口文档 | 直接覆盖成当前事实，不写"原来是…后来改成…"。**一个事实只写在一处**，别处给链接，不复制。 |
| **决策** | `PROJECT.md` 的"仍有效的决定" | 每条一行：日期 · 决定 · 一句原因。原因必须留，否则后来的人会把它当疏忽去"修"。被替代的决定从这里删掉，在履历里留一句"放弃 X，原因…"。 |
| **履历** | `PROJECT.md` 的"履历" | 每件事一句话，三种：`完成` · `失败`（带半句原因和"不要再…除非…"）· `放弃`（带原因）。细节去 git 查。 |
| **过程文件** | 评审报告、勘察报告、调研草稿、被推翻的方案、QA 截图 | 只为当前里程碑服务。里程碑结束时：有用的结论并进活文档，原文件删除（git 里能找回）。 |
| **合规证据**（受监管） | 合规矩阵的验证证据、测评要用的原件 | 放 `.team/evidence/`，不算文档，平时不读，不删。 |

"失败"条目最值钱：它防止下一个 Lead 或成员重复踩同一个坑。例：

```
失败  两个成员并行改根 pom.xml → 互相覆盖。共享文件只许一个任务改，其他任务依赖它
放弃  PACS 一期自研 → 需二类医疗器械注册，周期 12–18 月，排到二期
```

## 2. 什么时候更新

- **任务完成时**：只更新受这个任务影响的活文档。行为变了而文档没跟上，任务不算完成。
- **用户拍板时**：决定写进 `PROJECT.md`，被替代的旧决定挪成履历一句话；状态卡同步。
- **里程碑结束时**（关卡的一部分）：
  1. 过程文件：结论并进活文档，原文件删除。`.team/` 里只留 `STATE.md`、`guard.json`、`map.md`（代码库地图，按现状更新）、`brief-common.md`（成员 brief 的通用部分）、`evidence/`、当前在用的交接单。
  2. 履历：本里程碑完成了什么、哪些尝试失败、放弃了什么，各一句。
  3. 跑文档检查：`node <skill 目录>/scripts/doc-check.mjs <项目路径>`。它会查出活文档里残留的"待定 / 待拍板 / TODO"、指向不存在文件的链接、超长的状态卡和 STATE.md。有问题就修完再验收。

## 3. 复盘：把问题沉淀成会自动生效的东西

里程碑验收前做，结果写进验收材料，给用户看。

**第一步：列出本里程碑付出的"额外成本"。** 从任务板、评审、QA、STATE.md 里找：被退回的任务、返工、回滚、用户纠正、被刹车拦下的操作、同一处反复修改、成员之间的冲突。

**第二步：找共同根因。** 不是逐条描述现象，而是问"这几件事背后是不是同一个原因"。例如"CHANGELOG 被重建"和"pom.xml 被覆盖"的共同根因是"共享文件没有唯一负责人"。

**第三步：选沉淀方式**，按"越自动越好"的顺序：

| 方式 | 适用 | 落在哪 |
|---|---|---|
| 脚本 / 检查 | 能用程序判断对错的 | 加进 verify，或项目的检查脚本 |
| 刹车配置 | 要在动作发生时拦下的 | `.team/guard.json`（例如 verify 命令） |
| 项目规则 | 需要判断、但每个成员都必须知道的 | 状态卡的"必须 / 禁止"（自动注入给所有 agent） |
| skill 改进建议 | 换个项目也会犯的 | `.team/skill-feedback.md`，交付时交给用户决定是否改 skill。**不要自己改 skill 文件。** |
| 履历"失败"条目 | 一次性的、但值得后人知道的 | `PROJECT.md` 履历 |

出现过一次、代价也小的，写进履历就够了。出现两次及以上，或者一次就代价很大的，必须选前四种之一。

**输出格式**（放进验收材料）：

```
复盘 M<N>
| 根因 | 证据（哪几件事） | 沉淀方式 | 落在哪 |
没有沉淀的问题：<一行，说明为什么不值得>
```
