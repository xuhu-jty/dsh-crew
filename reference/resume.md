# 开工与接续

大项目会跨多个会话、多天、多次上下文压缩。Lead 的记忆不可靠，文件可靠。这一页决定你每次开工从哪里开始。

## 1. 判断：新项目还是接着做

看项目根目录：

- 有 `.team/STATE.md` → **接着做**，走第 2 节。不要重新做需求和方案，除非 `STATE.md` 里写着它们还没定。
- 没有 → 新项目，回到 SKILL.md 阶段 0。
- 用户说"接着做"但找不到 `STATE.md` → 问用户项目路径；还是没有，就按"已有代码库"当新项目处理，并告诉用户之前的过程记录不存在。

## 2. 恢复顺序（接着做时，按这个顺序读，读完再动手）

1. `.team/STATE.md`：当前里程碑、进行中的任务、阻塞、等用户回答的问题、最近的决定、上次停在哪一步。
2. `PROJECT.md`：目的、范围、方案、里程碑、决策记录（只读与当前里程碑相关的部分）。
3. 任务板：`team_task_list`。和 `STATE.md` 对账：任务板说进行中、但 `STATE.md` 没提的，以任务板为准并补进 `STATE.md`。**任务板为空但 `.team/TASKS-snapshot.md` 存在**，说明这是一次 Lead 轮换后的新会话：用快照重建未完成的任务。
4. `list_agents`：哪些成员还在、哪些已经不在。DHS 重启后，旧成员可能还能 `send_message` 继续，也可能不在了；不在的成员负责的 `in_progress` 任务，先 `release`，再派新人，用交接单交代背景。
5. `git status` 和 `git worktree list`：有没有未合并的分支、未提交的改动。来源不明的改动先问用户，不要丢弃。
6. 当前里程碑最近的评审和 QA 报告（`.team/` 下，看最新的一两份）。

读完后，给用户一段**三行以内**的接续说明：现在在哪个里程碑、上次做到哪、接下来做什么。有等用户回答的问题就一起问。然后继续推进。

## 3. 上下文被压缩之后（同一个会话里）

你会发现自己记不清细节。不要凭印象继续：重新读 `STATE.md` 和任务板，再接着做。这就是 `STATE.md` 存在的理由。

## 4. 主动换一个新会话（Lead 轮换）

Lead 自己的上下文也会越来越重，越到后面越容易忘掉早先的规则（跳过节点、超出授权提交、决定不入记录）。不要等用户发现，主动换一个干净的新会话接着做。

**什么时候换**（任一即换）：
- 一个里程碑验收完成后（最自然的切换点）。在节点④的验收问题里加一题"是否换新会话继续下一个里程碑"，推荐"是"。
- 你发现自己出现漂移的迹象：`STATE.md` 落后于实际进度、发现做了没记录的决定、对早先拍板的内容记不清、同一会话里已经被压缩过多次。
- 用户要求。

**怎么换**（按顺序，全部做完再结束本轮）：
1. 让正在跑的成员到一个干净的停点：完成当前任务或写好交接单（`templates/handoff.md`）；有未合并的 worktree 分支，在 `STATE.md` 里写清分支名和状态。
2. **保存任务板快照**：任务板属于当前根会话，新会话看不到。把 `team_task_list` 的全部任务（id、标题、状态、负责人、依赖、写入范围、描述要点）写进 `.team/TASKS-snapshot.md`。
3. 更新 `STATE.md`：当前阶段、下一步、等用户回答的问题、团队表（全部标"已退场"或写明交接单路径），以及"上次轮换：<时间>，原因"。
4. 用 `schedule_create` 开新会话：`target` 填 `new_once`，`rrule` 设成约 1 分钟后的一次性触发（例如 `DTSTART;TZID=Asia/Shanghai:<当前时间+1分钟，格式 YYYYMMDDTHHMMSS>` 换行 `RRULE:FREQ=DAILY;COUNT=1`），`title` 写"接续 <项目名>"，`prompt` 写：
   ```
   用 project-team skill 接着做 <项目绝对路径>。按 reference/resume.md 的恢复顺序读 .team/STATE.md、PROJECT.md、.team/TASKS-snapshot.md，用快照重建任务板，然后继续。
   ```
5. 告诉用户一句话：已开新会话"接续 <项目名>"，请打开它，并在输入框右下角模型名菜单里打开"启用智能体团队协作"（新会话默认关闭）。然后结束本轮，不再派活。

**新会话接手时**：按第 2 节恢复；任务板为空时，用 `.team/TASKS-snapshot.md` 重建（只建未完成的任务，已完成的在快照里保留记录即可）；旧会话的成员不在新会话的成员树里，需要的话按交接单派新成员。

## 5. 什么时候必须更新 STATE.md

- 用户拍板了任何决定（同时写进 `PROJECT.md` 决策记录）。
- 派出成员、成员完成、任务被退回。
- 里程碑开始、验收、结束。
- 你准备结束这一轮回复、等待用户之前。
- 发现了会影响后续的事实（某个库做不到、某个接口不可用）。

`STATE.md` 是给下一个 Lead 看的交接单，写当前事实和下一步，不写过程叙述。超过约 150 行就把已结束里程碑的内容压成一行，细节留在 `.team/` 的报告里。
