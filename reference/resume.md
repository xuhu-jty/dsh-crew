# 开工与接续

大项目会跨多个会话、多天、多次上下文压缩。Lead 的记忆不可靠，文件可靠。这一页决定你每次开工从哪里开始。

## 1. 判断：新项目还是接着做

看项目根目录：

- 有 `.team/STATE.md` → **接着做**，走第 2 节。不要重新做需求和方案，除非 `STATE.md` 里写着它们还没定。
- 没有 → 新项目，回到 SKILL.md 阶段 0。
- 用户说"接着做"但找不到 `STATE.md` → 问用户项目路径；还是没有，就按"已有代码库"当新项目处理，并告诉用户之前的过程记录不存在。

## 2. 恢复顺序（接着做时，按这个顺序读，读完再动手）

1. `.team/STATE.md`：当前里程碑、进行中的任务、阻塞、等用户回答的问题、最近的决定、上次停在哪一步。
2. `PROJECT.md`：目的、范围、方案、里程碑、决策记录（只读与当前里程碑相关的部分）。
3. 任务板：`team_task_list`。和 `STATE.md` 对账：任务板说进行中、但 `STATE.md` 没提的，以任务板为准并补进 `STATE.md`。
4. `list_agents`：哪些成员还在、哪些已经不在。DHS 重启后，旧成员可能还能 `send_message` 继续，也可能不在了；不在的成员负责的 `in_progress` 任务，先 `release`，再派新人，用交接单交代背景。
5. `git status` 和 `git worktree list`：有没有未合并的分支、未提交的改动。来源不明的改动先问用户，不要丢弃。
6. 当前里程碑最近的评审和 QA 报告（`.team/` 下，看最新的一两份）。

读完后，给用户一段**三行以内**的接续说明：现在在哪个里程碑、上次做到哪、接下来做什么。有等用户回答的问题就一起问。然后继续推进。

## 3. 上下文被压缩之后（同一个会话里）

你会发现自己记不清细节。不要凭印象继续：重新读 `STATE.md` 和任务板，再接着做。这就是 `STATE.md` 存在的理由。

## 4. 什么时候必须更新 STATE.md

- 用户拍板了任何决定（同时写进 `PROJECT.md` 决策记录）。
- 派出成员、成员完成、任务被退回。
- 里程碑开始、验收、结束。
- 你准备结束这一轮回复、等待用户之前。
- 发现了会影响后续的事实（某个库做不到、某个接口不可用）。

`STATE.md` 是给下一个 Lead 看的交接单，写当前事实和下一步，不写过程叙述。超过约 150 行就把已结束里程碑的内容压成一行，细节留在 `.team/` 的报告里。
