# 质量关卡

关卡不是形式。每一项都要拿得出证据；拿不出就写"未验证"，不能打勾。能交给脚本或插件判断的，交给脚本或插件。

## 任务关卡（成员自查，Lead 验收时抽查）

1. **做对了**：验收标准逐条满足，有证据；verify 通过（插件会在收工前检查改了代码有没有跑）。
2. **没多写**：走过复用阶梯（`roles/builder.md`），没有为"以后可能用"加的选项、抽象、配置、依赖。
3. **没少写**：调用方、测试、配置、导出都跟着改了；校验、错误处理、安全、无障碍没被省掉。
4. **有测试**：新逻辑里有分支、循环、解析、金额、安全、数据写入、修 bug 的，至少一个出错就会失败的测试。
5. **文档是当前的**：行为、接口、命令、配置、界面变了 → 同一任务里把对应活文档改成当前事实；没变就写"无行为变化"。
6. **界面连贯**（改了界面时）：符合 `DESIGN.md`；新功能的位置符合信息架构，回报里说明放在哪、为什么；加载、空、错误状态都有；面向用户的文字里没有内部术语（服务名、命令、ID、文件路径之外的技术字段、POC 编号）。
7. **写入范围内**：只改了任务声明的路径；越界的改动在回报里说明原因。
8. **真实数据核对**（功能读用户真实数据时）：只读地用真实数据跑一次，回报里附结果，并逐条说明可疑的数：恒为 0 或空、几乎全部落在同一状态、比例明显离谱、和平台自己显示的不一致。编出来的测试数据只能证明逻辑自洽，证明不了算对了。

## 退回修复

- 问题清单短（5 条以内）、改动集中：Lead 自己改，或新开一个只带这份清单的实现者。
- 原实现者还没收到过步数提醒：可以退回给它。已经跑了一百多步的不退回，换新人。
- 修完只复查改过的地方，不重新全面评审。复查交给原来的评审员：`send_message` 列出改了哪几条（对照评审编号），请它看改过的地方和有没有改出新问题；给已有成员发消息不占成员预算。改的人自己核对不算复查。
- 复查又提出要改的，改完再复查一次；来回超过 3 轮按 `reference/team-ops.md`「卡住时」处理。插件记着"最近一次评审之后有没有改过交付物"：没复查就拦下展示交付物、拉回交付。
- 原评审员已退场、预算用完、权限又是"从不询问"：停下告诉用户还差一次复查，请用户决定，不自己判定可以交付。

## 质量线：超预期

crew 交出去的东西要超出用户的预期；"没有错"和"达标"都只是平庸。阶段 1 就在成功标准里写下对标：这一类里最好的作品或产品是谁（写名字）。评审按"对标 = 10 分"打分，**12 分才算通过**：不输对标，并且至少有两处对标没有、用户没想到的东西，评审要写清是什么、在哪一章/哪个界面。说不出超在哪，就是平庸，结论只能是"还要改"；Lead 不能因为"没有硬伤"或"分数不低"就收下。

光有刹车和"必须修"，成员只学会别犯错。还要给它往上的拉力：每个里程碑在 `STATE.md` 记一行评分和"全书最好的一章"，分数往下走就是警报；评审的"要保持"一节交给下一批成员照着写；关键场写两版、评审挑一版。

## 评审关卡（`roles/reviewer.md`）

按重要性：正确 → 安全 → 预期负载下撑得住 → 有测试 → 够快 → 精简。每条问题都要有具体触发情形。结论只有 `可以合入` 或 `先修 X、Y`。

## 里程碑关卡（Lead 组织，按顺序）

1. **集成**：合并后的主分支 verify 通过；主流程实际跑一遍（有界面就桌面和手机宽度各一次）；已有项目的特征测试全部仍通过（计划内的行为变化在决定里有记录）。
2. **界面一致性**：设计师或评审员对照 `DESIGN.md` 和信息架构检查这一批界面（有 `impeccable` 用它的 critique/audit）。
3. **复用和重复**：这一批里有没有几乎相同、改时必须一起改的代码？有就开任务合并。
4. **任务板对账**：每个验收标准都有已完成的任务，或写在"不做"里；最后一个里程碑对照整个全貌。
5. **文档**：用户可见的变化都有文档（`roles/docs.md` 的覆盖表）；过程文件清理、履历更新（`reference/docs-and-retro.md` §2）；`node <skill 目录>/scripts/doc-check.mjs --milestone <项目路径>` 通过（含代码地图对账、过程文件已清）。
6. **复盘沉淀**：按 `reference/docs-and-retro.md` §3 做，结果放进验收材料。
7. **清理**：`git worktree list` 只剩主目录；没有游离的未合并分支；没有还在跑的成员。
8. **验收演示（节点④）**：先说清哪些是产品界面、哪些只是技术验证。给用户一份短材料 —— 怎么运行、演示步骤、关键截图、逐条对照验收标准、**你需要知道的三件事**（这次改了什么、哪里最可能出问题、怎么撤回）、团队替你定的事（回报里的"偏离"）、遗留问题、想法池（`reference/changes.md` §4）让用户勾选。复盘结果附在后面，用户想看再看。受监管项目另核对本里程碑涉及的合规条目都有验证证据。用户确认后才算结束：按授权提交、更新状态卡和 STATE.md、细化下一个里程碑。
