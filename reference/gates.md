# 质量关卡

关卡不是形式。每一项都要能拿出证据；拿不出就写"未验证"，不能打勾。

## 任务关卡（每个任务完成前，成员自查；Lead 验收时抽查）

1. **做对了**：验收标准逐条满足，有证据（命令输出、测试结果、截图）；`verify` 通过（有 `verify` 时）。
2. **没多写**：走过复用阶梯（见 `roles/builder.md`），没有为了"以后可能用"而加的选项、抽象、配置；没有新加一个只为省几行的依赖。
3. **没少写**：调用方、测试、配置、导出都跟着改了；校验、错误处理、安全、无障碍没有被省掉。
4. **有测试**：新逻辑里有分支、循环、解析、金额、安全、数据写入、修 bug 的，至少一个在出错时会失败的测试。纯展示、纯配置可以没有。
5. **文档跟上**：行为、接口、命令、配置、界面变了 → 对应文档在同一个任务里更新（README、`PROJECT.md`、`DESIGN.md`、`CHANGELOG.md` 中相关的那个）。没变就写"无行为变化"。
6. **界面连贯**（改了界面时）：符合 `DESIGN.md` 的颜色、字体、间距、组件；新功能的位置符合信息架构，并在任务回报里说明放在哪、为什么；加载、空、错误状态都有。
7. **写入范围内**：只改了任务声明的路径；越界的改动在回报里说明原因。

## 评审关卡（评审员执行，见 `roles/reviewer.md`）

按重要性排序：正确 → 安全 → 在预期负载下撑得住 → 有测试 → 够快 → 精简。每条问题都要有具体触发情形，没有具体情形的不算问题。结论只有两种：`可以合入` 或 `先修 X、Y`。

## 里程碑关卡（一组相关任务完成后，Lead 组织）

1. **集成**：构建通过，全部测试通过，主流程实际跑一遍（有界面就打开看渲染结果，桌面和手机宽度各一次）。
2. **界面一致性**：设计师或评审员对照 `DESIGN.md` 和信息架构检查这一批改动的界面（有 `impeccable` 时用它的 critique/audit），确认新功能没有显得突兀、没有打乱已有布局。
3. **文档覆盖**：文档成员（或 Lead）为这一批用户可见的变化做覆盖表：

   ```
   条目            参考说明    操作指南    设计理由
   /api/orders     README ✅   ❌          PROJECT.md ✅
   导出按钮        ❌          ❌          ❌        ← 缺口
   ```

   完全没有文档的条目是缺口，开任务补上。文档里的架构图、目录说明和代码不一致的地方也要修。
4. **复用和重复**：这一批里有没有几乎相同、改的时候必须一起改的代码？有就开任务合并。
5. **任务板对账**：本里程碑的每个验收标准都有已完成的任务，或者写在"不做"里；最后一个里程碑还要对照整个全貌。
6. **不退化**：`verify` 在合并后的主分支上通过；已有项目的特征测试全部仍然通过（行为变化是计划内的，要在 `PROJECT.md` 决策记录里有对应条目）；`git worktree list` 里本里程碑的 worktree 已合并清理。
7. **验收演示（节点④）**：给用户一段短材料 —— 怎么运行/打开、演示步骤、关键截图、对照本里程碑验收标准的逐条结果、遗留问题。同时回顾想法池（`reference/changes.md` §4），让用户勾选哪些排进下个里程碑。用户确认后才算里程碑结束：按授权提交、更新 `STATE.md`（里程碑状态、学到的事、下一个里程碑的细化）。受监管项目另外核对：本里程碑涉及的合规矩阵条目是否都有验证证据。
