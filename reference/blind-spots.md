# 完成整个项目容易漏掉的点

阶段 2 做方案时过一遍，把相关的写进全貌、任务板，或写进"不做"并说明原因。阶段 6 收尾时再过一遍，没处理的写进交付报告的"风险"。不相关的条目跳过，不要为了凑全而硬做。

## 产品与体验

- 第一次使用：空数据时看到什么？怎么引导到第一个有价值的结果？
- 出错后能不能自己恢复（重试、撤销、保留已填内容）？
- 长文本、零结果、超大数据量、慢网络、断网。
- 移动端宽度、键盘操作、读屏、对比度（无障碍）。
- 文案：错误提示说人话、告诉用户下一步怎么办。
- 多语言、时区、日期和数字格式（需要时）。

## 工程

- 输入校验在信任边界上（用户输入、外部接口返回、LLM 输出）。
- 错误处理不吞异常、不丢数据；写操作的顺序和事务。
- 并发：先查后写的竞态、重复提交、幂等性。
- 性能：每条数据一个查询（N+1）、只增不减的内存或列表、热路径里的重复计算。
- 依赖：真的需要新依赖吗？许可证兼容吗？版本锁了吗？
- 配置和密钥：不进代码库，有 `.env.example` 或等价说明。
- 数据迁移与回滚：旧数据怎么办？迁移失败怎么回去？
- 日志：出问题时能从日志看出发生了什么，且不泄露隐私。

## 安全

- 鉴权和越权（能不能看到/改别人的数据）。
- 注入（SQL、命令、HTML/XSS、路径穿越）。
- 文件上传、外部 URL 抓取（SSRF）。
- 敏感信息出现在日志、错误信息、前端代码里。

## 交付与运行

- 怎么在一台新机器上从零跑起来（README 里的步骤真的能跑通吗）。
- 构建、部署、发布渠道（代码没有分发方式就没人能用）。
- 备份、监控、出错时谁会知道。
- 版本号和 CHANGELOG。

## 大项目特有

- 跨会话丢进度：`STATE.md` 是不是最新的？换一个新会话只读它能不能接着做？
- 计划写死太早：后面的里程碑是不是已经细化到任务了？（应该只写一句目标）
- 方向偏了很久才发现：每个里程碑有没有给用户演示验收？
- 改坏老功能：要改的模块有没有特征测试？`verify` 是不是每次合并都跑？
- 并行对不上：模块之间的接口有没有先写下来？改接口有没有先通知？
- worktree 和分支残留：里程碑结束时有没有合并、清理？有没有游离的未合并分支？
- 成员越用越差：有没有按任务簇或里程碑换人？交接单有没有写？
- 测试夹具里硬编码了"今天"：跑到第二天就会误报。日期从被测系统或固定时钟派生。
- 依赖用户提供的东西（账号、密钥、测试环境）：有没有一次性列清楚？没有时有没有替身让工作继续？

## 团队协作本身（DHS 特有）

- **写入范围不是锁**：`write_scopes` 重叠只给警告。同时进行的写任务必须路径不重叠，或者串行。
- **任务状态变化不会唤醒任何成员**：每次交接、退回、解除阻塞，都要 `send_message`。
- **成员看不到 Lead 的对话**：brief 不自包含，成员就会猜。
- **成本**：每个成员都是独立会话，按 token 计费。只读评审可以并行，写代码的成员不超过 3 个；成员干完就不要再给它发消息。
- **失控的成员**：长时间无进展、反复改同一处、评审来回超过 3 轮 —— 停下来，换思路或问用户。
- **开发者预览**：DHS 会有破坏性变更。交付报告里写明 DHS 版本，升级后先用小项目试一次本手册。
- **没有版本控制就没有回滚**：并行改文件前先确认是 git 仓库；提交由刹车插件弹窗请用户批准。
- **刹车插件没装或被关**：提交审批、收工前验证、状态卡检查都会退化成靠自觉。开工时确认插件在，交付报告写明。
- **提示词层面的东西会决定 agent 会不会绕刹车**：装了改写系统提示词的插件（例如让模型"把拒绝当重试"的破甲类插件），任何靠自觉的规则都会失效。发现这类插件，告诉用户风险，由用户决定。
- **状态卡过期**：状态卡会自动注入给所有 agent，过期比没有更糟。里程碑关卡的文档检查会查它的长度，内容由 Lead 对照 STATE.md 确认。
