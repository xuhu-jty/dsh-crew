# 交付报告模板（阶段 6，交给用户）

```
# <项目名> 交付报告

## 一句话结论
现在可以 <做什么>；还差 <什么> 才算完全达成目的。

## 你需要知道的三件事
1. 这次改了什么（用户能感觉到的变化）
2. 哪里最可能出问题（以及出了问题会看到什么）
3. 怎么撤回（回到哪个版本、要做什么）

## 团队替你定的事
做的过程中计划没写到、团队按稳妥做法定下的事（来自成员回报的"偏离"）。不同意的可以提出来改。

## 对照成功标准
| 标准 | 状态 | 证据 |
|---|---|---|
| … | 达成 / 部分 / 未达成 | .team/qa/… 或测试名或命令 |

## 做了什么
按模块或用户流程列，每条附证据位置。

## 没做什么
| 项目 | 原因 | 建议 |
（包括用户选择"以后再说"的和团队没来得及做的）

## 未验证
实际没执行的检查、缺一手证据的判断、依赖的外部假设。

## 上线前必须由有资质的人完成的事（受监管项目必填）
| 事项 | 依据 | 谁来做 | 状态 |
（测评、认证、备案、接口接入审批、临床/业务安全评审等；团队不能替代）

## 合规矩阵完成情况（受监管项目）
已满足并有验证证据 N 条 · 设计上满足但需外部测评 N 条 · 未满足或未核实 N 条（逐条列出）

## 变更记录
本次共 N 个变更请求：现在做 N / 下个里程碑 N / 想法池 N / 不做 N（详见 PROJECT.md）

## 复盘沉淀
各里程碑复盘出的根因，以及沉淀成了什么（脚本 / 刹车配置 / 项目规则 / 履历）。
给 skill 的改进建议见 `.team/skill-feedback.md`（由你决定要不要改 skill）。

## 刹车与用量
刹车插件版本 · 被拦下的主要情况（提交审批、收工前验证、状态卡、成员预算、步数提醒）· 没装或关闭的原因。
用量：流水线底部"用量"的总数和最多的那一个；比预期多的原因（复盘时用）。

## 风险与需要你注意的点
按影响排序。来自 blind-spots 检查、评审、QA 的未关闭问题。

## 文档
更新了哪些文档；从哪里开始读（入口）。

## 怎么运行
从零跑起来的命令（已在干净环境验证过 / 未验证）。

## 建议的下一步
最多 3 条，按价值排序。

## 过程记录
团队编制与原因 · 任务数（完成/退回次数）· 用户拍板次数 · DHS 版本
```
